# Padlet Sender

웹 패널에서 **게시판 주소·게시물 개수·제목·내용·전송 간격**을 입력하고 실행하면, 서버가 봇 전용 익명 세션을 만들고 전송합니다. 사용자의 Padlet 로그인 상태를 바꾸거나 수동으로 게시할 필요가 없습니다.

- 웹 패널: https://dev-cat0.github.io/padlet/
- 서버: https://padlet-sender-panel.onrender.com

## 사용 방법

먼저 디스코드 봇에서 키를 발급받습니다. 사이트의 키 입력 창에서 인증하면 자체 백엔드가 키를 검증한 뒤 임의 세션 토큰만 발급합니다. **키는 최초 인증 요청에만 포함되고, 이후 요청에는 세션 토큰만 사용합니다.** 브라우저 저장소에는 원본 키를 저장하지 않습니다. 최초 요청의 키는 본인의 개발자 도구에서 확인할 수 있습니다. [로컬 봇 설치·명령어·키 운영 안내](keybot/README.md)를 참고하세요.

봇은 `start-keybot.cmd`로 백그라운드 실행하며 CMD 창을 닫아도 유지됩니다. 키 기록은 Firebase Cloud Firestore에 저장하므로 로컬 봇이 꺼져 있어도 사이트 인증·차감·기한 검사·사용 로그가 동작합니다. 소진·만료된 키는 실행 버튼이 잠기고 서버도 새 실행을 거부합니다.

1. 인증 후 다섯 항목을 입력하고 **실행**을 누릅니다. 다회용 키는 새 실행 접수마다 1회 차감합니다.
2. 실행 현황에 익명 세션 준비, 전송 성공 수, 오류 사유가 표시됩니다.
3. **중지**는 준비 단계에서도 사용할 수 있습니다. 이미 전송 중인 요청은 결과를 받은 뒤 멈춥니다.
4. **긴급 삭제**를 누르면 전송을 멈추고, 진행 중인 게시 응답까지 확인한 뒤 **현재 패널 세션의 모든 실행에서 보낸 게시물**을 삭제합니다. 여러 게시판에 실행한 기록도 포함합니다. 삭제 대상·삭제 확인·오류 수를 화면에서 확인할 수 있고, 실패한 항목은 버튼을 다시 눌러 재시도할 수 있습니다. 429 요청 제한은 표시된 대기 시간이 지난 뒤 다시 시도하세요.

긴급 삭제는 생성 성공 응답의 게시물 hashid와 해당 봇의 익명 세션을 사용합니다. 다른 사람이 작성한 글이나 게시판 전체 목록을 삭제 대상으로 수집하지 않습니다. 삭제는 이 패널에서 복구할 수 없습니다. 성공 응답에 hashid가 없으면 ‘추적 불가’로 표시하고, 네트워크 오류로 생성 여부를 확인하지 못한 글도 자동 삭제를 보장하지 않습니다. 이 기능 추가 전에 보낸 글, 서버 재시작 전 기록, 만료된 패널 세션의 기록은 자동 삭제할 수 없습니다.

게시물 개수는 **섹션당 게시물 수**입니다. 매 주기마다 모든 섹션에 각각 1건씩 요청합니다. 예를 들어 섹션 3개, 개수 10, 간격 0.3초이면 0.3초마다 세 섹션에 1건씩, 총 30건을 전송합니다. 섹션이 없는 게시판은 주기당 1건입니다. 기본값은 섹션당 50건 / 0.3초이며 개수 0은 모든 플랜에서 무제한입니다. 영구 플랜 외에는 실행당 섹션별 개수를 최대 5,000개까지 지정할 수 있습니다. 영구 플랜의 기존 숫자 입력 상한(1,000,000개)은 유지됩니다. 모든 간격에서 앞선 회차의 응답을 기다리지 않고 다음 회차를 시작할 수 있습니다. 한 번에 진행하는 요청은 최대 32건이며, 섹션 1개면 최대 32회차, 3개면 최대 10회차를 겹쳐 처리합니다. 섹션이 32개보다 많으면 한 회차 안에서 최대 32건씩 처리합니다. 동시 처리 한도에 도달하면 응답을 기다리며, 밀린 회차를 만회하려고 설정 간격보다 짧게 몰아서 보내지는 않습니다. 0은 추가 대기 없는 최대 속도입니다. 실제 처리량은 Padlet 응답과 요청 제한에 따라 달라집니다.

전송·삭제 작업은 서버에서 진행되므로 웹 페이지를 닫아도 계속될 수 있습니다. 전송을 멈추려면 중지를 누르세요. 삭제 기록은 같은 탭을 새로고침해도 패널 세션이 유지되면 사용할 수 있습니다. 작업이 끝난 뒤 30분간 패널에 접속하지 않으면 세션이 만료됩니다. 서버 재시작·세션 만료 시 메모리의 작업·익명 삭제 자격 정보·게시물 기록은 사라집니다.

## 익명 봇과 자동 준비

- 웹 패널은 `/api/run`에 다섯 입력값만 보냅니다. 사용자 Padlet 쿠키나 계정 정보를 받지 않습니다.
- 작업마다 서버 내부에 새로운 브라우저 컨텍스트를 만들고, 로그인이 없는 익명 방문자 정보와 게시판 쓰기 권한을 확인합니다. 사용자에게 브라우저 화면을 보여주거나 조작을 요구하지 않습니다.
- 게시판 초기 상태·섹션·필수 입력 항목을 GET으로 조회합니다. 준비용 테스트 게시물은 만들지 않습니다.
- 제목·내용만으로 필수 항목을 채울 수 없는 게시판은 사유를 표시하고 게시 전에 중단합니다.
- 전송은 봇의 같은 익명 세션 안에서 처리합니다. 작업이 끝나면 브라우저를 닫고, 긴급 삭제에 필요한 봇의 쿠키·CSRF·UID와 게시물 hashid만 서버 메모리에 보관합니다. 디스크나 웹 패널로 내보내지 않습니다. 삭제할 때 해당 익명 세션을 경량 브라우저에 복원하고, 모두 삭제한 실행의 자격 정보는 폐기합니다. 사용자 계정에 로그인하지 않으며 로그인 정보가 발견되면 중단합니다.
- 자동 준비에서는 화면 표시용 이미지·동영상·폰트·스타일시트와 실시간 소켓 연결을 차단합니다. 초기 익명 세션을 얻은 뒤 같은 브라우저 컨텍스트 안에 로컬 경량 페이지를 만들고 원래 게시판 화면을 닫습니다. 쿠키·CSRF·UID는 같은 세션에서 유지하며, 게시판 앱의 렌더링·게시글 목록·실시간 갱신이 전송과 자원을 경쟁하지 않도록 합니다. 무료 서버의 메모리를 고려해 한 번에 하나의 브라우저 작업을 실행합니다.
- 자동 준비는 전체 앱 스크립트의 로딩 완료 대신 CSRF·UID가 준비됐는지 확인합니다. 외부 스크립트가 지연돼도 익명 세션이 준비되면 경량 페이지로 전환합니다. 접속 시간 초과, 세션 정보 누락, 브라우저 종료는 구분하여 표시하며 서버 로그에는 실패 단계·예외 종류만 기록합니다.
- 403·보안 확인·익명 쓰기 금지는 오류로 중지합니다. 보안 확인을 자동으로 해결하거나 접근 제한을 우회하지 않습니다.
- 429가 감지되면 모든 회차의 새 요청을 멈추고 진행 중인 응답을 수집한 뒤 Retry-After와 대기 시간을 따릅니다. 성공한 요청은 다시 보내지 않습니다. 네트워크 오류처럼 성공 여부가 불명확하면 재전송하지 않습니다.

## 구성과 배포

- `web/`: 다섯 입력란과 실행·중지·긴급 삭제·활동 로그 화면. GitHub Pages로 배포합니다.
- `server/app.py`: 세션·상태·실행·중지·긴급 삭제 API. `/api/run`과 `/api/emergency-delete`는 작업을 접수한 뒤 곧바로 응답합니다. 삭제 API는 클라이언트가 전달한 게시물 ID를 사용하지 않고 인증된 패널 세션의 기록만 처리합니다.
- `server/engine.py`: 익명 자동 준비, 매 주기 전체 섹션 동시 전송, 중지와 세션 정리.
- `server/browser.py`: 서버 내부 브라우저와 같은 출처의 요청 처리.
- `server/anonymous.py`, `server/fields.py`: 익명 상태·섹션·입력 항목 확인.
- 이전 연결·캡처 API는 현재 화면에서 사용하지 않습니다. 수동 브라우저 조작 API는 실행 횟수 차감을 우회할 수 있어 차단했습니다.

`main`의 `web/` 변경은 GitHub Pages 워크플로로 배포합니다. Render는 기존 `padlet-sender-panel` Docker 서비스를 사용합니다. Playwright 이미지와 Python 패키지 버전은 1.58.0으로 맞춥니다. 세션이 메모리에 있으므로 서버 worker와 인스턴스는 각각 하나로 유지합니다.

## 검증

```powershell
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m playwright install chromium
.\.venv\Scripts\python tests/ui_smoke.py
.\.venv\Scripts\python tests/automatic_smoke.py
.\.venv\Scripts\python tests/preparation_smoke.py
node --check web/app.js
```

서버 테스트와 Chromium 모의 통합 테스트로 한 번의 실행 요청, 익명 준비, 준비용 게시물 없는 전송, 매 주기 전체 섹션 동시 전송과 섹션당 개수, 로그인 사용자 차단, 필수 항목 검증, 준비 중 중지와 리소스 정리를 확인합니다. 실제 게시판 검증에서는 생성 요청을 보내기 전에 차단하며 게시물을 작성하지 않습니다.
